# Контракт получения и контроля данных WB

Статус: рабочий контракт первой версии, составленный по официальной документации WB API. Технические поля сопоставлены с документацией; бизнес-классификация операций должна быть проверена на обезличенной фактической выгрузке перед публикацией правил расчёта.

## Как читать документ

Контракт определяет, какие данные Grafio запрашивает у WB, как понимает завершённость загрузки и что делает при дублях, поздних изменениях или ошибке источника. Он не утверждает бизнес-смысл поля только по его названию.

На первом чтении пройдите «Источники первой версии», маппинг обязательных полей, правила полноты и сверку. Подробности пагинации и ошибок нужны для реализации и приёмки интеграции.

## Источники первой версии

| Код | Источник | Обязательность | Назначение |
|---|---|---|---|
| FIN-LIST | `POST /api/finance/v1/sales-reports/list` | Обязателен | Найти недельный отчёт и получить его контрольные итоги |
| FIN-DETAIL | `POST /api/finance/v1/sales-reports/detailed/{reportId}` | Обязателен; метод за период — резервный вариант | Получить операции отчёта для расчёта и детализации |
| ACQ-DETAIL | Отчёт об издержках на приём платежей | Контрольный | Проверить эквайринг; не суммировать повторно с `acquiringFee` финансовой детализации |
| ADV-SPEND | `GET /adv/v1/upd` | Опционален | Фактические расходы кампаний для рекламного расхода и ДРР |
| ADV-STATS | `GET /adv/v3/fullstats` | Опционален | Статистика и атрибуция кампаний; отдельно от факта списания средств |

Для финансовых методов нужен токен категории «Финансы», для рекламных — категории «Продвижение». Токен относится к конкретному кабинету; данные разных кабинетов не смешиваются в одной загрузке.

## Ограничения официального API

| Область | Подтверждённое ограничение | Решение Grafio |
|---|---|---|
| Список отчётов | Данные с 01.01.2025; до 1000 отчётов, пагинация `offset`; один запрос в минуту на кабинет | Загружать страницы последовательно и соблюдать лимит отдельно для каждого кабинета |
| Детализация по ID | Данные с 01.01.2025; до 100 000 строк за ответ | Использовать ID найденного отчёта; для недоступной страны регистрации применять метод за период |
| Детализация за период | Данные с 29.01.2024 | Использовать как резерв и для более ранних доступных периодов |
| Пагинация деталей | Начать с `rrdId = 0`, затем передавать `rrdId` последней строки до ответа `204` | Загрузка считается технически завершённой только после `204` |
| Деньги | В новых методах денежные поля имеют тип `string` | Разбирать как точное десятичное значение; исходную строку сохранять |
| Период | `weekly` или `daily`, даты RFC3339, время Москва UTC+3 | UC-01 запрашивает `weekly`; границы сверяются с ПН–ВС |
| Реклама | `adv/v3/fullstats`: до 31 дня, до 50 кампаний, 3 запроса в минуту | Делить кампании на группы и агрегировать только после получения всех групп |
| Рекламные расходы | `adv/v1/upd`: период от 1 до 31 дня | Запрашивать недельный интервал и хранить фактические списания отдельно от статистики |

Устаревший `GET /api/v5/supplier/reportDetailByPeriod` в новый контракт не включается.

## Поля финансового источника

| Бизнес-смысл | Поля-кандидаты WB | Статус сопоставления |
|---|---|---|
| Идентичность отчёта | `reportId`, `dateFrom`, `dateTo`, `createDate`, `reportType`, `currency` | Подтверждено |
| Идентичность строки | `rrdId` вместе с кабинетом и `reportId` | Рабочий ключ; уникальность проверяется на загрузке |
| Товар | `nmId`, `vendorCode`, `title`, `techSize`, `sku` | Подтверждено; связь может отсутствовать |
| Тип операции | `docTypeName`, `sellerOperName`, `bonusTypeName` | Подтверждено как признаки классификации; перечень значений не считается закрытым |
| Даты | `orderDt`, `saleDt`, `rrDate` | Подтверждено наличие; смысл основного среза закрепляется тестом отчётного периода |
| Продажи до возвратов | `retailPriceWithDisc`, `quantity`, `docTypeName`, `sellerOperName`; `retailAmount` — контрольный кандидат | Старая книга использует аналог `retailPriceWithDisc`, но не умножает его на количество. Формулу для строк с `quantity > 1`, корректировок и сторно нужно проверить на контрольной неделе |
| Возвраты | `retailPriceWithDisc`, `quantity`, `docTypeName`, `sellerOperName`; `retailAmount` — контрольный кандидат | Старая книга берёт модуль аналога `retailPriceWithDisc`; знак, количество и сторно проверяются на контрольной неделе |
| Выкупы | Рассчитываются как продажи до возвратов минус возвраты | Это бизнес-показатель Grafio, а не готовое поле API |
| Комиссия | `ppvzSalesCommission`, `commissionPercent`, `kvw` и связанные поля | Требуется определить денежное поле без двойного учёта |
| Логистика | `deliveryService`; направление — по виду операции и связанным признакам | Сумма-кандидат подтверждена, разделение прямой/обратной требует теста |
| Эквайринг | `acquiringFee` | Подтверждено поле; отдельный отчёт используется для сверки, а не второго начисления |
| Хранение | `paidStorage` | Подтверждено |
| Операции на приёмке | `paidAcceptance` | Подтверждено |
| Штраф | `penalty`, детализация причины через `bonusTypeName`/вид операции | Подтверждено поле суммы |
| Прочие удержания | `deduction` | Подтверждено поле; категория определяется правилом |
| Доплата/компенсация | `additionalPayment` и вид операции | Поле подтверждено; брак и ущерб требуют проверки значений классификатора |
| Перевыставленная логистика | `rebillLogisticCost`, `rebillLogisticOrg` | Подтверждено; отдельная статья до решения о группировке |
| Утилизация | вид операции и соответствующее денежное поле | Специальное поле документацией не подтверждено; выявляется по фактическим значениям |
| К перечислению | `forPay` | Подтверждено поле, не подменяет выручку или банковскую оплату |

`deliveryAmount` и `returnAmount` нельзя объявлять стоимостью логистики только по названию. Их единица и роль проверяются на ответе API и контрольном отчёте.

Подробная трассировка полей старой книги к новому API и перечень ещё не выполненных проверок приведены в [валидации маппинга](wb-field-mapping-validation.md). До завершения контрольной сверки `retailPriceWithDisc` и `retailAmount` сохраняются как разные исходные поля и не подменяют друг друга.

## Контрольные итоги отчёта

FIN-LIST предоставляет суммы `retailAmountSum`, `forPaySum`, `deliveryServiceSum`, `paidStorageSum`, `paidAcceptanceSum`, `deductionSum`, `penaltySum`, `additionalPaymentSum` и `bankPaymentSum`. Для каждой поддержанной статьи Grafio сравнивает сумму деталей с соответствующим итогом списка отчётов.

```text
Расхождение = сумма классифицированных деталей − контрольная сумма FIN-LIST
```

Сверка проходит только при точном расхождении 0 в полной расчётной точности. Любое ненулевое значение переводит её в состояние «Требует проверки». `bankPaymentSum` проверяет банковский итог отчёта, но не является выручкой или выкупами.

## Алгоритм загрузки

1. Для кабинета запросить FIN-LIST с `period = weekly` и найти отчёт с точными границами недели.
2. Сохранить метаданные и контрольные итоги отчёта.
3. Запросить FIN-DETAIL с `rrdId = 0`; продолжать от последнего `rrdId` до `204`.
4. Сохранить неизменённый ответ источника и разобранные известные поля. Неизвестный ключ схемы регистрировать как изменение источника.
5. Проверить валюту, формат денег, границы периода, дубли ключей и завершение пагинации.
6. Классифицировать строки только опубликованной версией правил. Новое значение вида операции оставить нераспределённым.
7. Выполнить сверку с FIN-LIST и создать версию отчёта со ссылками на использованные загрузки.

Повторный запрос не перезаписывает прежнюю загрузку. Если изменились строки, контрольные суммы или хеш ответа, создаются новая загрузка и новая версия отчёта. Частота повторной проверки закрытых недель является настройкой Grafio и должна быть уточнена по фактической частоте корректировок WB.

## Полнота и ошибки

| Ситуация | Состояние источника | Реакция отчёта |
|---|---|---|
| Отчёт найден, все страницы получены, структура разобрана, сверка пройдена | Полные данные | Рассчитывать зависимые показатели |
| Получена только часть страниц или произошёл `429` до завершения | Не определена / загрузка не завершена | Повторить после допустимого интервала; не публиковать зависимые итоги |
| `204` при поиске ожидаемого завершённого отчёта | Данных пока нет | Показать отсутствие отчёта и время последней проверки |
| `400` | Ошибка запроса | Не повторять без исправления параметров |
| `401` | Ошибка доступа | Запросить восстановление подключения кабинета |
| `429` | Ограничение частоты | Повторить с задержкой согласно лимиту метода |
| Новое поле или значение операции | Методика требует проверки | Сохранить данные, показать нераспределённую операцию, уведомить администратора |
| Любое ненулевое расхождение сверки | Требует проверки | Показать обе суммы и точное расхождение; не назначать причину автоматически |
| Рекламный источник отключён | Не входит в состав отчёта | Финансовый отчёт остаётся полным, ДРР не рассчитывается |
| Рекламный источник включён, но не завершён | Неполные данные рекламы | Рекламные расходы и зависимые итоги не рассчитываются |

Получение всех страниц означает техническую полноту ответа, но не доказывает бизнес-полноту. Для публикации нужны также успешный разбор, контроль ключей и доступные сверки.

## Защита от двойного учёта

- `acquiringFee` финансовой детализации и отдельный отчёт эквайринга являются двумя представлениями одной области; один источник выбирается расчётным, второй — контрольным.
- Расходы продвижения из ADV-SPEND и рекламное удержание в финансовом отчёте не суммируются без доказательства, что это разные операции.
- Итоговая группа и входящие в неё строки не складываются одновременно.
- Повторно полученный `cabinet + reportId + rrdId` не создаёт новую операцию внутри одной загрузки.
