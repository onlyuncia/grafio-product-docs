# Валидация маппинга финансовых полей WB

Статус: этап 1 завершён в части документальной трассировки. Для окончательного подтверждения бизнес-формул требуется один обезличенный ответ нового финансового API за контрольную неделю.

## Коротко

**Зачем документ:** доказать переход от столбцов старой Excel-оцифровки к полям нового финансового API WB и не принять похожее название за подтверждённую формулу.

**Главное решение:** используются три уровня подтверждения. П1 показывает формулу старой книги, П2 — техническое поле нового API, П3 — точное совпадение на обезличенной контрольной неделе. До П3 маппинг остаётся кандидатом.

**Пример:** цена с согласованной скидкой в книге сопоставлена с `retailPriceWithDisc`, но знак, заполненность и поведение на возвратах ещё нужно проверить на фактическом ответе.

При первом чтении достаточно разделов «Что считается подтверждением», «Трассировка основных полей» и «Что остаётся открытым».

## Цель

Документ связывает четыре уровня: исходную строку WB, столбец старой книги, правило расчёта и показатель Grafio. Такая цепочка нужна, чтобы изменение схемы или нового значения операции можно было обнаружить, объяснить и проверить без догадок по названию поля.

## Что считается подтверждением

| Уровень | Смысл |
|---|---|
| П1 · книга | В старой книге найден исходный столбец и фактическая формула его обработки |
| П2 · API | В актуальном финансовом API найдено соответствующее техническое поле |
| П3 · контроль | Формула воспроизведена на обезличенном ответе API и сошлась с контрольными итогами с точным расхождением 0 |
| О · открыто | Однозначного соответствия пока нет; показатель нельзя публиковать как проверенный |

Наличие П1 и П2 ещё не означает П3. Оно подтверждает происхождение кандидата, но не доказывает, что новый API передаёт значения и знаки так же, как старая выгрузка.

## Исправленная гипотеза по продажам и возвратам

Ранее в контракте основным кандидатом было указано `retailAmount`. Проверка формул книги показала более точную связь:

```text
столбец BN
«Цена розничная с учётом согласованной скидки»
→ старое retail_price_withdisc_rub
→ новое retailPriceWithDisc
```

Это меняет кандидата, но ещё не завершает проверку. Во всех 28 447 строках продажи и возврата исследованной книги количество равно 1, поэтому книга не отвечает на вопрос, является ли `retailPriceWithDisc` суммой строки или ценой единицы при `quantity > 1`. На контрольной выгрузке нужно сравнить как минимум две формулы:

```text
Вариант A = retailPriceWithDisc
Вариант B = retailPriceWithDisc × quantity
Контроль = retailAmount и итог retailAmountSum
```

Выбирается формула, которая одновременно объясняет строки с количеством больше 1, корректировки, сторно и итог отчёта. До этого `retailPriceWithDisc` и `retailAmount` хранятся раздельно.

## Протокол контрольной сверки

1. Выбрать закрытую неделю с продажей, возвратом, логистикой, штрафом или компенсацией. Желательно наличие строки с `quantity > 1`.
2. Получить запись FIN-LIST с точными границами недели и сохранить все контрольные суммы.
3. Получить все страницы FIN-DETAIL до ответа `204`. Сохранить исходный ответ без преобразований.
4. Проверить валюту, границы периода, число строк и уникальность `cabinet + reportId + rrdId`.
5. Построить перечень новых ключей схемы и фактических значений `docTypeName`, `sellerOperName`, `bonusTypeName`.
6. Рассчитать каждый кандидат отдельно. Не сворачивать неизвестные операции в «Прочие» до проверки администратором.
7. Сравнить суммы деталей с FIN-LIST и ручным контрольным расчётом. Допуска нет: расхождение в полной расчётной точности должно быть равно 0.
8. Для каждого показателя сохранить результат: формулу, использованные поля, тестовые строки, контрольную сумму, расхождение и решение.
9. Только после успешной сверки повысить статус до П3 и разрешить публикацию зависимой метрики.

## Минимальный набор контрольных случаев

| Случай | Что доказывает |
|---|---|
| Обычная продажа и возврат | Базовые знаки и формула выкупов |
| `quantity > 1` | Нужность умножения цены на количество |
| Сторно продажи и сторно возврата | Полноту классификатора операций |
| Прямая и обратная логистика | Разделение `deliveryService` по направлению |
| Корректировка эквайринга | Отсутствие двойного учёта |
| Штраф с причиной и товаром | Детализацию аномалии до операции |
| Брак, ущерб или потеря | Денежное поле и знак компенсации |
| Хранение и платная приёмка | Сверку с отдельными итогами отчёта |
| Утилизация | Самостоятельную статью и её денежный источник |
| Новое значение операции | Перевод строки в нераспределённые и сигнал администратору |

## Результат этапа

Документально подтверждены происхождение и технические кандидаты для основных финансовых показателей. Обнаружена и исправлена преждевременная гипотеза о поле продаж. Незакрытый риск сосредоточен в бизнес-интерпретации значений нового API: количестве, знаках, сторно, компенсациях и утилизации.

Следующий шаг этого этапа — выполнить протокол на одном обезличенном ответе нового API. До его появления можно переходить к проектированию логической модели данных, сохраняя статусы кандидатов.
