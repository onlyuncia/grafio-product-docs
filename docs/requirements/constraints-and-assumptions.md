# Ограничения и допущения Grafio

Здесь разделены ограничения проектного решения и предположения, которые требуют подтверждения до промышленного запуска.

## 1. Продуктовые ограничения

| ID | Ограничение | Последствие для решения |
|---|---|---|
| CON-01 | Первая версия обязательного финансового контура использует данные Wildberries и завершённые недельные периоды. | Другие маркетплейсы и свободный месячный пересчёт не входят в исходный расчётный сценарий. |
| CON-02 | Рекламные расходы и ДРР доступны только при согласованном полном источнике. | Отсутствующий источник не подменяется нулём. |
| CON-03 | Управление рекламными кампаниями, настройками WB и автоматический сбор новостей/тарифов не входят в продуктовый контур. | Grafio не обещает автоматически объяснять изменение тарифа или причины отклонения. |
| CON-04 | Admin Console — внутреннее полноэкранное пространство Grafio. | Она не является клиентским разделом sidebar и не использует canvas. |
| CON-05 | «Мой дашборд» — личное представление доступных метрик. | Виджеты не меняют корпоративные показатели, методику или права других участников. |
| CON-06 | Сводный финансовый отчёт нескольких кабинетов не входит в физическую модель первой версии. | Кабинеты остаются самостоятельным контекстом до отдельного проектирования консолидации. |

## 2. Технические и интеграционные ограничения

| ID | Ограничение | Последствие для решения |
|---|---|---|
| CON-07 | Получение финансовых данных зависит от доступности, лимитов и контракта API WB. | Загрузка идемпотентна, выполняется фоново и не блокирует чтение опубликованных отчётов. |
| CON-08 | Изменение схемы или семантики полей WB нельзя считать безопасным без проверки. | Новые поля и типы фиксируются как наблюдение качества до обновления контракта и нормализатора. |
| CON-09 | Демонстрационный мокап использует синтетические данные и локальное состояние. | Прототип не подтверждает фактические авторизацию, интеграцию, расчёт, аудит и хранение данных. |
| CON-10 | Целевые NFR требуют испытаний на реальном профиле нагрузки и согласования политики хранения. | Их нельзя заявлять как достигнутые эксплуатационные показатели до испытаний. |

## 3. Допущения, требующие валидации

| ID | Допущение | Как подтвердить | Владелец решения |
|---|---|---|---|
| ASM-01 | Поля нового финансового API WB позволяют устойчиво идентифицировать операцию и исключить дубли. | Сверка на одной обезличенной фактической неделе и контрактные тесты. | Системный аналитик / интеграция |
| ASM-02 | Контрольные суммы WB сопоставимы с расчётной моделью Grafio без скрытой агрегации. | Пройти контрольную сверку по фактическому отчёту и документировать расхождения. | Финансовый эксперт и системный аналитик |
| ASM-03 | Продажа и возврат могут быть связаны с достаточной достоверностью для расчёта себестоимости. | Проверить ключи и альтернативные варианты связи на фактических данных. | Системный аналитик |
| ASM-04 | Источник рекламы даёт достаточную полноту для ДРР и не дублирует финансовое удержание WB. | Сопоставить источники, период и денежные компоненты на контрольной выборке. | Финансовый эксперт и системный аналитик |
| ASM-05 | Стартовый профиль NFR соответствует первым коммерческим клиентам. | Замерить реальную нагрузку пилота и пересмотреть профиль перед запуском. | Владелец продукта / DevOps |
| ASM-06 | Сроки хранения и основания удаления соответствуют договору и применимым требованиям. | Утвердить с юридической и коммерческой функциями до запуска. | Владелец продукта |

## Управление изменениями

Ограничение меняется только через решение о границах продукта. Допущение закрывается результатом проверки: «подтверждено», «опровергнуто» или «заменено». Изменение, затрагивающее требования, отражается также в SRS и матрице трассировки.

Источники: [SRS](srs.md), [контракт WB](../data/wb-data-contract.md), [NFR](non-functional-requirements.md).
