# Сводный реестр требований первой версии Grafio

Статус: требования первой версии одобрены автором. Это исходный реестр идентификаторов для трассировки. Отдельные аналитические представления требований собраны в [бизнес-требованиях](business-requirements.md), [пользовательских требованиях](user-requirements.md), [функциональных требованиях](functional-requirements.md), [бизнес-правилах](business-rules.md), [НФТ и атрибутах качества](non-functional-requirements.md), [ограничениях и допущениях](constraints-and-assumptions.md) и [требованиях к интерфейсам](interface-requirements.md).

## Как читать документ

Требования переводят пользовательский сценарий в проверяемые обязательства системы. На первом чтении достаточно бизнес-требований и функциональных требований. Информационные требования объясняют необходимые данные, требования качества — свойства результата, а права участников — допустимые действия ролей.

Каждое требование содержит основание и способ проверки. Полная связь с проектными решениями и приёмкой собрана в [матрице прослеживаемости](traceability-matrix.md).

## Обозначения

| Префикс | Вид требования |
|---|---|
| BR | Бизнес-требование: какой результат нужен участникам |
| FR | Функциональное: что должна делать система |
| IR | Информационное: какие данные необходимы |
| QR | Требование качества: какие свойства результата обязательны |
| AR | Права участника |

Каждая строка содержит основание и способ проверки. Ссылки UC относятся к [пользовательскому сценарию](weekly-expense-use-case.md).

## Права участников

| ID | Участник | Разрешено | Не входит в полномочия |
|---|---|---|---|
| AR-01 | Менеджер / аналитик | Просматривать доступные кабинеты, сравнивать недели, раскрывать статьи, настраивать налог юридического лица и вести пользовательские расходы в пределах выданного доступа | Изменять общие правила классификации операций и публиковать версии методики |
| AR-02 | Владелец / клиент | Просматривать отчёт, детализацию, статусы качества, уведомления и доступные версии | Изменять методику расчёта; редактирование налогов и расходов не предоставляется базовой ролью |
| AR-03 | Администратор Grafio | Исследовать неизвестные операции, менять и публиковать правила, запускать предусмотренный пересчёт, указывать область действия и выпускать уведомления | Изменять пользовательские расходы или налоговую настройку клиента без отдельного клиентского полномочия |

Права применяются только к доступным пользователю кабинетам и юридическим лицам. Детальная модель разграничения доступа будет построена на этапе концептуальной модели данных.

| FR-07 | Система должна рассчитывать себестоимость, итог расходов, маржу в рублях и маржинальность в процентах по утверждённым паспортам показателей | UC шаги 5–6 | Для контрольного набора входов результат совпадает с паспортами метрик |

| IR-05 | Категория расходов | код, название, родительская группа, правило знака, версия и период действия | Единая структура расходов и отсутствие двойного учёта |

| IR-11 | Версия отчёта | версия правил, снимок входных данных, время расчёта, включённые опции, состояние качества | Открытие и сравнение воспроизводимых результатов |

Измеримые требования к производительности, доступности, восстановлению, безопасности, хранению, наблюдаемости и совместимости собраны в [стартовом коммерческом профиле NFR](non-functional-requirements.md).

## Требования качества

| ID | Требование | Проверка |
|---|---|---|
| QR-01 | Один набор входов, настроек и версий должен давать одинаковый результат при повторном расчёте | Повторный расчёт контрольного примера совпадает по всем показателям |
| QR-02 | Промежуточные расчёты не должны округляться до суммирования; пользовательская точность отображения не влияет на расчёт и контроль | Контрольный пример с копейками не накапливает расхождение при любой настройке отображения |
| QR-03 | Отсутствие, ноль и невозможность расчёта должны быть разными состояниями | Для каждого состояния интерфейс и данные возвращают различимые значение и причину |
| QR-04 | Значение показателя должно быть прослеживаемо до версии формулы и исходных операций | Из значения открываются паспорт, версия отчёта и доступная расшифровка |
| QR-05 | Таблица, диаграмма и детализация должны использовать один контекст и версию | Суммы выбранной недели совпадают между представлениями с учётом явно обозначенной неполноты |
| QR-06 | Опубликованная версия отчёта не должна изменяться незаметно | Пересчёт создаёт новую версию; исходная остаётся доступной согласно UC A8 |
| QR-07 | Изменение правила должно иметь автора, причину, дату и область действия | У версии нельзя отсутствовать ни одному из перечисленных реквизитов |
| QR-08 | Во время проверки методики пользователь должен видеть состояние работ и область возможного изменения | Проверка сценария UC A7 подтверждает доступность разделов и предупреждения |
| QR-09 | Контрольные сообщения должны объяснять действие пользователя | Для неполноты, выкупов ≤ 0, расхождения и неизвестной операции указаны разные причины и следующий шаг |

## Независимые состояния отчёта

Чтобы одно сообщение не скрывало другое, состояния хранятся по отдельным измерениям:

| Измерение | Значения первой версии |
|---|---|
| Получение источника | загружается / получен / ошибка получения |
| Полнота | полные данные / неполные данные / не определена до завершения загрузки |
| Сверка | пройдена / требует проверки / неприменима |
| Методика | актуальна / исследуется / опубликована новая версия |
| Показатель | рассчитан / не рассчитывается с причиной |

Например, отчёт может одновременно иметь полный финансовый источник, отсутствующую рекламу, пройденную финансовую сверку и нерассчитанный ДРР. Система не должна сводить такую ситуацию к одному общему статусу «ошибка».

## Проверка границ

- Требования не включают другие маркетплейсы, месячный сценарий, управление рекламой, автоматический сбор новостей, поисковые конверсии и региональную аналитику.
- Прежние графики рекламы, логистики и заказов рассматриваются как основания для дальнейшего развития; они не расширяют основной финансовый сценарий первой версии.
