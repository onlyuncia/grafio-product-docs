# Нефункциональные требования и атрибуты качества Grafio

Нефункциональные требования задают целевые свойства первой версии. Численные ориентиры пока являются проектными допущениями: перед коммерческим запуском их нужно подтвердить испытаниями, эксплуатационными данными, договором и применимыми правовыми требованиями.

## Коротко

**Зачем документ:** задать измеримые условия, при которых функции Grafio можно считать пригодными для первой коммерческой версии.

**Главное решение:** скорость и устойчивость проверяются на одном стартовом профиле — до 50 активных кабинетов, 10 одновременных пользователей, 5 параллельных загрузок и 250 000 операций в крупном недельном отчёте.

**Пример:** требование «отчёт открывается быстро» заменено проверяемой целью: p95 открытия опубликованного отчёта с историей 16 недель — не более 3 секунд на согласованном профиле.

Значения в документе являются целями проектирования, а не результатами испытаний. При первом чтении достаточно профиля нагрузки, требований NFR-01–NFR-06 и раздела «Приоритеты при конфликте».

## Как читать требования

Нефункциональные требования описывают не новую функцию, а качество работы уже определённых функций: скорость, доступность, восстановление, безопасность и управляемость.

| Вид | Значение |
|---|---|
| Обязательное свойство | Нарушение делает решение недопустимым независимо от нагрузки, например изоляция клиентов или отсутствие токена в журнале |
| Целевое значение | Измеримая характеристика стартового профиля, например p95 времени ответа |
| Бизнес-допущение | Временное решение, которое нельзя вывести из исходных данных, например срок хранения raw-ответа |

## Проверочный профиль нагрузки

Показатели производительности проверяются на согласованном профиле, а не на пустой базе.

| Параметр | Значение стартового профиля |
|---|---:|
| Активные кабинеты | до 50 |
| Одновременные интерактивные пользователи | до 10 |
| Параллельные фоновые загрузки | до 5 с отдельным ограничителем WB на кабинет |
| Один крупный недельный финансовый отчёт | до 250 000 операций |
| Нормализованные финансовые операции в тестовой базе | до 10 млн |
| История на основном экране | 16 недель |
| Страница детализации | 100 операций |

Это сертификационный профиль первой версии, а не программное ограничение. Превышение объёма должно измеряться и планироваться, а не приводить к скрытому усечению данных.

## Производительность и своевременность

| ID | Требование | Условия измерения |
|---|---|---|
| NFR-01 | p95 открытия опубликованного недельного отчёта с историей 16 недель — не более 3 секунд | Поддерживаемый браузер, прогретое приложение, тестовый профиль; включает получение и отображение основных данных |
| NFR-02 | p95 открытия первой страницы детализации статьи — не более 5 секунд | До 250 000 операций в недельном отчёте, страница 100 строк, применены обычные фильтры категории/товара |
| NFR-03 | Команда загрузки, проверки правила или пересчёта подтверждается с `job_id` не более чем за 2 секунды | Подтверждение не ждёт завершения фоновой работы |
| NFR-04 | Не менее 95% недельных финансовых отчётов профиля рассчитываются или получают объяснимый конечный статус не позднее 60 минут после появления отчёта в FIN-LIST | Действующий токен; WB отвечает в пределах своего контракта; длительный внешний `429` и недоступность WB учитываются отдельно |
| NFR-05 | Изменение состояния фонового задания становится видимым пользователю или администратору не позднее 60 секунд | Состояние берётся из Grafio, без нового обращения интерфейса к WB |
| NFR-06 | Система обрабатывает проверочный профиль без потери, усечения и двойного учёта операций | Итоговая скорость не может достигаться пропуском страниц или отключением проверок |

`p95` означает, что не менее 95% измеренных операций укладываются в целевое время. Измерение фиксирует набор данных, версию приложения и условия теста.

## Доступность и устойчивость

| ID | Требование | Проверка |
|---|---|---|
| NFR-07 | Доступность чтения уже опубликованных отчётов — не менее 99,5% за календарный месяц | Синтетический запрос к API отчётов; плановые работы учитываются отдельно и объявляются заранее |
| NFR-08 | Ошибка или недоступность WB не должна блокировать чтение ранее опубликованных отчётов | Отключить адаптер WB и открыть существующий отчёт |
| NFR-09 | Повтор временно упавшего этапа продолжает обработку с последней подтверждённой границы без дублей | Прервать пагинацию и повторить задание |
| NFR-10 | RPO для правил, настроек, версий отчёта и исходных загрузок — не более 1 часа | Восстановить состояние из резервной копии и измерить максимально потерянный интервал |
| NFR-11 | RTO основной функции чтения отчётов — не более 4 часов | Тестовое восстановление после недоступности основного хранилища |
| NFR-12 | Восстановление из резервной копии проверяется не реже одного раза в квартал | Сохранён протокол восстановления, время и обнаруженные проблемы |

`RPO` показывает допустимый объём потери последних данных по времени. `RTO` показывает допустимое время восстановления функции. Значения являются стартовыми целями, а не фактом достигнутой эксплуатации.

## Безопасность и изоляция

| ID | Требование | Проверка |
|---|---|---|
| NFR-13 | Пользователь не может получить данные организации, юрлица или кабинета вне своей области доступа | Негативные тесты для API, выгрузки, прямых ссылок и идентификаторов других клиентов |
| NFR-14 | Передача данных выполняется по защищённому соединению; рабочие хранилища и резервные копии шифруются | Проверка конфигурации транспорта, хранилищ и резервных копий |
| NFR-15 | Токены WB хранятся в защищённом хранилище по `secret_ref` и не попадают в БД аналитики, команды, raw-ответы, журналы и сообщения об ошибках | Автоматический поиск тестового секрета во всех перечисленных каналах |
| NFR-16 | Административные роли используют многофакторную аутентификацию; создание проекта правила отделено от полномочия публикации | Проверка ролей, входа и запрещённых действий |
| NFR-17 | Существенные действия администратора записываются в неизменяемый аудит с автором, временем, областью и изменением | Попытка изменить/удалить событие отклоняется; цепочка расследования восстанавливается |

Конкретные алгоритмы и версии шифрования выбираются при физическом проектировании и поддерживаются согласно политике безопасности. В логах используются внутренние идентификаторы и безопасные описания ошибок.

## Хранение и удаление

| ID | Требование | Стартовое бизнес-допущение |
|---|---|---|
| NFR-18 | Политика хранения задаётся по типу данных и выполняется контролируемым заданием | Raw-ответы — минимум 1 год; операции, опубликованные отчёты, версии правил и аудит — минимум 3 года |
| NFR-19 | Истечение срока не удаляет объект, на который ссылается ещё хранимая опубликованная версия отчёта | Зависимости проверяются до удаления; при конфликте удаление блокируется и регистрируется |
| NFR-20 | Удаление данных клиента выполняется по подтверждённому основанию, с журналом состава и результата | Точные сроки после прекращения договора устанавливаются коммерческой и правовой политикой до запуска |

Указанные сроки не объявляются законодательной нормой. Они нужны для оценки объёма хранилища и должны быть подтверждены владельцем продукта.

## Наблюдаемость и сопровождаемость

| ID | Требование | Проверка |
|---|---|---|
| NFR-21 | Для загрузки, проверки правила и пересчёта доступна сквозная трассировка по `correlation_id`, `job_id`, `load_id` и версии отчёта | По версии отчёта восстанавливается цепочка этапов, попыток и ошибок |
| NFR-22 | Контролируются возраст заданий, ошибки WB, продвижение пагинации, изменения схемы, сверки, неизвестные операции и полнота пересчёта | Для каждого сигнала существует метрика/журнал и маршрут к ответственному |
| NFR-23 | Контракты команд, событий и нормализации версионируются; несовместимое изменение не применяется без миграции или нового обработчика | Контрактный тест старой и новой версии; неизвестная версия отклоняется объяснимо |
| NFR-24 | Ошибка содержит безопасный код, этап, время и `correlation_id`, достаточные для поиска причины без исходного секрета | По сообщению находится диагностическая запись; токен и полный raw-ответ отсутствуют |

Численные пороги эксплуатационных оповещений настраиваются после первых замеров. Отсутствие порога не отменяет сбор соответствующего сигнала.

## Удобство и совместимость

| ID | Требование | Проверка |
|---|---|---|
| NFR-25 | Основной отчёт, детализация и административный процесс доступны с клавиатуры; фокус видим, поля имеют подписи, состояние передаётся не только цветом | Ручное прохождение сценариев без мыши и проверка состояний |
| NFR-26 | Основные пользовательские сценарии поддерживаются в двух последних стабильных основных версиях Chrome и Edge | AC-01, AC-10 и административный AC-17 выполняются в заявленных браузерах |
| NFR-27 | Сообщения о неполноте, сверке и методике содержат причину и следующее доступное действие понятным языком | Проверка текстов по AC-07—AC-09 и AC-17, включая примеры AT-02 и AT-03 |

Требование доступности интерфейса сформулировано через проверяемое поведение. Формальное соответствие внешнему стандарту не заявляется без отдельного аудита.

## Приоритеты при конфликте

1. Изоляция клиентов, точность денег и отсутствие двойного учёта имеют приоритет над скоростью.
2. Полнота обязательного источника имеет приоритет над сроком публикации.
3. Чтение опубликованного отчёта имеет приоритет над новой фоновой загрузкой.
4. При перегрузке фоновые задания ограничиваются очередью; интерактивное чтение не должно вытесняться массовым пересчётом.
5. Система не снижает качество незаметно: превышение цели производительности видно в наблюдаемости.

## Приёмка профиля

Условия измерения заданы требованиями `NFR-*` выше. Фактические результаты производительности, доступности и восстановления появятся только после реализации и испытаний; до этого требования имеют статус целевых.

Пользовательский отчёт и административный процесс представлены в [кликабельном прототипе](../../prototype/README.md) на синтетических данных.

## Качество финансового результата

Идентификаторы `QR-01—QR-09` задают проверяемые свойства расчёта, представления и версионирования. `QR-02`, `QR-06` и `QR-09` проверяют уже сформулированные правила, не вводя параллельных норм. Измеримые эксплуатационные цели заданы требованиями `NFR-*` выше.

| ID | Требование | Проверка |
|---|---|---|
| QR-01 | Один набор входов, настроек и версий должен давать одинаковый результат при повторном расчёте | Повторный расчёт контрольного примера совпадает по всем показателям |
| QR-02 | Проверять соблюдение [RULE-05](business-rules.md) на агрегировании и в разных режимах представления | Контрольный пример с копейками даёт одинаковый точный результат при любой настройке отображения |
| QR-03 | Отсутствие, ноль и невозможность расчёта должны быть разными состояниями | Для каждого состояния интерфейс и данные возвращают различимые значение и причину |
| QR-04 | Значение показателя должно быть прослеживаемо до версии формулы и исходных операций | Из значения открываются паспорт, версия отчёта и доступная расшифровка |
| QR-05 | Таблица, диаграмма и детализация должны использовать один контекст и версию | Суммы выбранной недели совпадают между представлениями с учётом явно обозначенной неполноты |
| QR-06 | Проверять неизменяемость версии по [RULE-10](business-rules.md) при пересчёте | Прежняя версия остаётся доступной для сравнения по альтернативному потоку UC-01/A8 |
| QR-07 | Изменение правила должно иметь автора, причину, дату и область действия | У версии нельзя отсутствовать ни одному из перечисленных реквизитов |
| QR-08 | Во время проверки методики пользователь должен видеть состояние работ и область возможного изменения | Проверка альтернативного потока UC-01/A7 подтверждает доступность разделов и предупреждения |
| QR-09 | Проверять [NFR-27](#удобство-и-совместимость) для каждого контрольного состояния | Для неполноты, выкупов ≤ 0, расхождения и неизвестной операции указаны разные причины и следующий шаг |
