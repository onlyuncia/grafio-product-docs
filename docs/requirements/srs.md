| Атрибут | Значение |
|---|---|
| Статус | Спецификация сервиса: реализованные разделы и целевые решения |
| Версия | 1.0 |
| Предмет | Недельная финансовая аналитика WB, планы, клиентское рабочее пространство, реализованные РНП и Товары, целевая Студия, внутренняя Admin Console |
| Тип документа | SRS: единый контракт требований, без выбора технологий реализации |
| Источник истины для формул | [Паспорта показателей](../data/metric-passports.md) |
| Источник условий приёмки | [Критерии приёмки](acceptance-criteria.md) и [NFR](non-functional-requirements.md) |

## 1. Назначение

Grafio помогает продавцу Wildberries получать воспроизводимый недельный финансовый результат: выручку, выкупы, расходы, себестоимость, маржу и маржинальность. Пользователь видит качество данных, версию методики и детализацию до доступных операций. Система отделяет факты источника от методики расчёта, а клиентскую работу — от внутреннего управления правилами Grafio.

Этот SRS собирает согласованный объём работ для команды разработки. Он ссылается на подробные артефакты, а не повторяет формулы, модель данных и интеграционные последовательности. При расхождении приоритет имеют документы, указанные в таблице «Нормативные ссылки».

## 2. Границы системы

### 2.1 Входит в объём

1. Недельный финансовый отчёт по доступному кабинету WB.
2. Получение, нормализация, контроль качества и версионирование финансовых данных WB.
3. Классификация операций, сверка, детализация и версии отчёта.
4. Клиентский «Контроль расчётов»: кейс, доказательства, задачи и передача запроса в Grafio.
5. Внутренняя Admin Console для исследования системной проблемы и публикации методики.
6. Недельные и месячные планы с сопоставлением факта и плана.
7. Недельная аналитика и личный «Мой дашборд» с KPI и поддержанными графиками.
8. Управление командой организации и базовые функции безопасности.
9. РНП с дневными и недельными показателями, каталог товаров и библиотека виджетов Студии.

### 2.2 Не входит в объём

- управление рекламными кампаниями и настройками Wildberries;
- автоматическое установление причины изменения показателя;
- автоматический сбор новостей и тарифов маркетплейса;
- самостоятельная публикация системной методики клиентом;
- другие маркетплейсы в обязательном финансовом контуре первой версии;

## 3. Пользователи и права

| Роль | Основная задача | Ключевые полномочия |
|---|---|---|
| Владелец клиента | Контролировать результат организации и команду | Просмотр всех данных своей организации, управление участниками, отправка и закрытие кейсов |
| Финансист | Сверить и объяснить финансовый результат | Детализация, сверка, кейсы, доказательства и задачи |
| Аналитик | Исследовать показатели и тенденции | Отчёты, графики, планы, личный дашборд, дополнение кейсов |
| Менеджер | Исполнить назначенную работу | Назначенные задачи, планы и комментарии в своей области |
| Просмотр | Ознакомиться с опубликованным результатом | Только чтение доступных данных |
| Администратор Grafio | Изменить системную методику контролируемо | Admin Console, правила, контроль, публикация и аудит |

Роль администратора Grafio не является ролью клиентской организации. Доступ проверяется на уровне организации, юридического лица, кабинета и действия.

## 4. Контекст и внешние системы

```text
Wildberries API (проектный финансовый сценарий)
   → контур получения и нормализации Grafio
   → контроль качества / классификация / расчёт
   → неизменяемая версия отчёта
   → клиентское рабочее пространство

Ozon API (существующая синхронизация Grafio)
   → существующие аналитические разделы; финансовый сценарий Ozon в этой SRS не определён

клиентский кейс
   → внутренняя Admin Console Grafio
   → версия методики / пересчёт или применение вперёд
   → результат в клиентском кейсе
```

| Внешняя сторона | Назначение взаимодействия | Нормативный источник |
|---|---|---|
| Wildberries API | Финансовые отчёты и, при подтверждённом источнике, рекламные данные | [Контракт WB](../data/wb-data-contract.md) |
| Ozon API | Существующая синхронизация маркетплейса; проектные финансовые правила Ozon не описываются | [Технический обзор реализации](../architecture/implementation-baseline.md) |
| Клиент | Читает отчёты, настраивает планы, создаёт кейсы и управляет командой | [Пользовательские требования](user-requirements.md) |
| Admin Console Grafio | Управляет системными правилами и выпуском версий | [Операционные процессы](../processes/operational-workflows.md) |

## 5. Функциональные требования

Функциональный набор сгруппирован по предметным областям, а не по очередности разработки. Требования содержат как описанное поведение сервиса, так и целевые решения; статус частей указан в [архитектуре Grafio](../architecture/README.md). Подробные формулировки и критерии находятся в [функциональных требованиях](functional-requirements.md).

| Блок | Обязательное поведение | Связанные требования |
|---|---|---|
| Контекст и отчёт | Выбор области и недели; показатели, качество источников, версия методики, контроль сверки | PFR-01—PFR-08 |
| Качество и методика | Независимые состояния, неизвестные операции, клиентский кейс, Admin Console, публикация и версии | PFR-09—PFR-16 |
| Планы и аналитика | Версионный план, совместимое сравнение с фактом, тематические графики и личный dashboard | PFR-17—PFR-23 |
| Команда и безопасность | Роли, персональная безопасность, разделение контуров и аудит действий | PFR-24—PFR-27 |
| Настройки финансового результата | Пользовательские расходы и налоговая настройка юридического лица | PFR-28—PFR-29 |
| Существующие продуктовые разделы | РНП по дням и неделям, каталог и себестоимость товаров, библиотека KPI и графиков Студии | PFR-30—PFR-34 |

### 5.1 Критические сценарии

1. **Просмотр недели.** Пользователь выбирает кабинет и завершённую неделю, видит результат, качество, версию, структуру и доступную историю.
2. **Исследование отклонения.** Пользователь открывает статью или точку графика, переходит к товарам и операциям, при необходимости создаёт кейс.
3. **Проблема расчёта.** Grafio автоматически фиксирует изменение схемы, неизвестную операцию или расхождение в Admin Console; клиент может добавить отдельный кейс. Администратор проверяет причину и область, проходит контроль, при необходимости публикует новую версию, а клиент видит статус и решение.
4. **Пересчёт.** Публикация новой методики создаёт новые версии затронутых недель либо применяется вперёд с выбранной даты. Опубликованная история не перезаписывается.
5. **План-факт.** Пользователь создаёт план для явной области, активирует версию и видит сравнение только с совместимым фактом.
6. **Личный dashboard.** Пользователь начинает с пустого листа, добавляет поддержанный KPI или график и изменяет его только в режиме редактирования.

## 6. Данные и бизнес-правила

### 6.1 Данные

Система хранит отдельно:

- клиентскую организацию, юридические лица, кабинеты и области доступа;
- исходные неизменяемые ответы маркетплейсов и состояние загрузки (финансовый сценарий первой версии детализирован для WB);
- нормализованные операции, суммы, товарные связи и контрольные итоги;
- правила классификации, категории, настройки налога и пользовательские расходы;
- версии отчёта, версии планов, кейсы качества и аудит действий.

Обязательные ключи, связи, типы и инварианты определены в [Логической модели данных](../data/logical-data-model.md).

### 6.2 Обязательные правила

| Правило | Требование к реализации |
|---|---|
| Период | Неделя отчёта — ровно ПН–ВС; незавершённая неделя не выдаётся за финальный результат. |
| Денежные значения | Хранятся и рассчитываются с полной точностью; форматирование не влияет на расчёт и сверку. |
| Состояния | Ноль, отсутствие и невозможность расчёта различимы в данных и интерфейсе. |
| Сверка | Успех — только `Δ = 0` до пользовательского округления. |
| Методика | Правило имеет автора, причину, область, период и версию; кабинетное исключение требует обоснования. |
| История | Пересчёт создаёт новую версию отчёта; старую нельзя скрыто изменить. |
| План | План не меняет факт и сравнивается только с одинаковыми областью, единицей и методикой. |
| Полномочия | Клиент предлагает решение в кейсе; методику публикует только администратор Grafio. |

Полный набор бизнес-правил: [Бизнес-правила Grafio](business-rules.md).

## 7. Требования к интерфейсам

### 7.1 Пользовательский интерфейс

| Интерфейс | Требование |
|---|---|
| Рабочее пространство клиента | Общий toolbar передаёт контекст организации, кабинета и периода; разделы не скрывают качество данных. |
| Отчёт и аналитика | Метрика, единица, период, методика, тип графика и значения точек читаемы; сравнимые серии используют одну временную основу. |
| Контроль расчётов | Кейс отображает проблему, период, сумму, статусы, доказательства, ответственного и следующее действие. |
| Планы | Форма блокирует несовместимое сравнение и показывает версию, дату действия и статус. |
| Мой дашборд | Пустое начальное состояние; сетка и canvas-инструменты видимы только в этом разделе. |
| Admin Console | Отдельный полноэкранный контур без клиентского sidebar и canvas; есть очередь, правило, контроль, публикация и возврат. |
| Команда и безопасность | Роли, 2FA, сессии и ключи разделены на ясные самостоятельные действия. |

### 7.2 Программные и интеграционные интерфейсы

1. Интерфейс не вызывает WB API при каждом открытии отчёта; чтение использует опубликованную версию Grafio.
2. Загрузка, проверка правила и пересчёт выполняются асинхронно; команда возвращает `job_id` не позднее 2 секунд на стартовом профиле.
3. Контракты нормализации, команд и событий версионируются. Несовместимое изменение требует миграции или отдельного обработчика.
4. Ошибка возвращает безопасный код, этап, время и `correlation_id`, без секрета и полного raw-ответа.
5. Взаимодействие с WB поддерживает пагинацию, идемпотентный повтор и terminal-ответ завершения по правилам [Интеграционная спецификация Grafio](../architecture/integration-specification.md).

## 8. Атрибуты качества и ограничения

| Аспект | Обязательство |
|---|---|
| Производительность | p95 открытия опубликованного недельного отчёта с 16 неделями истории — не более 3 секунд на стартовом профиле. |
| Доступность | Чтение опубликованных отчётов — не менее 99,5% в месяц; сбой WB не блокирует уже опубликованный результат. |
| Устойчивость | Повтор фонового этапа продолжает обработку без дублей; RPO до 1 часа, RTO чтения до 4 часов. |
| Безопасность | Изоляция по области доступа, защищённая передача и хранение, MFA для административных ролей, защищённое хранилище токенов. |
| Аудитируемость | По отчёту, правилу или задаче восстанавливается цепочка действий, версии и источники входных данных. |
| Доступность UI | Основные пути проходят с клавиатуры, имеют видимый фокус и не кодируют смысл только цветом. |
| Совместимость | Основные пути поддержаны в двух последних стабильных версиях Chrome и Edge. |

Полные условия измерения и стартовый профиль нагрузки: [Нефункциональные требования](non-functional-requirements.md). Продуктовые ограничения и требующие проверки допущения: [Ограничения и допущения Grafio](constraints-and-assumptions.md).

## 9. Приёмка

Реализация принимается, когда:

1. выполнены связанные [критерии приёмки](acceptance-criteria.md); ключевые случаи проиллюстрированы [сквозными примерами](acceptance-criteria.md);
2. выполнены отрицательные проверки изоляции, неизвестной операции, неполноты, нулевой/отрицательной базы и ненулевой сверки;
3. пройдены контрактные проверки интеграции WB, пагинации, повтора и версионирования;
4. сценарии ролей и административной публикации подтверждают запрет клиенту менять методику;
5. целевые NFR проверены на согласованном нагрузочном профиле;
6. каждое обязательное требование имеет состояние в [матрице трассировки](traceability-matrix.md).
