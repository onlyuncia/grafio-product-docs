# ADR-001. Модульный монолит с отдельным асинхронным worker

| Атрибут | Значение |
|---|---|
| Статус | Принято |
| Дата | 2026-04-29 |
| Решение | Backend развивается как модульный монолит; длительные операции выполняет отдельный worker-процесс. |

## Контекст

Финансовый контур должен согласованно управлять доступом, версиями методики, расчётами, отчётами, кейсами и аудитом. При этом загрузка WB, нормализация и пересчёт могут быть долгими и не должны удерживать HTTP-запрос.

## Альтернативы

1. Один монолитный процесс без worker — простая разработка, но фоновые операции конкурируют с чтением отчётов.
2. Микросервисы для каждого предметного модуля — независимое масштабирование, но преждевременная сложность: сеть, согласованность, развёртывание и наблюдаемость.
3. Модульный монолит с worker — чёткие границы при общей транзакционной модели и отдельном масштабировании тяжёлых задач.

## Решение

Выбрана третья альтернатива. Модули остаются в одном серверном приложении и одной PostgreSQL-базе, но владеют своими командами, событиями и сущностями. Worker получает задания из Redis и выполняет загрузку, нормализацию, проверку качества, расчёт и пересчёт.

## Последствия

- Версии, правила и аудит сохраняют транзакционную целостность без распределённых транзакций.
- Worker можно масштабировать отдельно от API.
- Перенос модуля в самостоятельный сервис допускается после подтверждённой нагрузки или независимого жизненного цикла.
- Границы модулей обязательны: общий доступ к чужим данным не заменяет контракт между модулями.
