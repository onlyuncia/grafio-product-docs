# Реализованная основа Grafio

Этот обзор фиксирует техническую основу сервиса, разработанного с нуля. Общая схема и статус модулей находятся в [архитектуре Grafio](README.md).

## Как устроен сервис

| Слой | Реализация | Роль в системе |
|---|---|---|
| Клиентское приложение | React, TypeScript, Vite | РНП, товары, планы, дашборд, настройки и аккаунт |
| API | Fastify, Prisma, PostgreSQL | Доступ, организации, кабинеты маркетплейсов, продуктовые данные и настройки |
| Фоновые задания | BullMQ, Redis, отдельный worker | Загрузка данных WB и Ozon, обновление агрегатов |
| Аналитическое чтение | PostgreSQL, materialized views | Подготовленные показатели для экранов и отчётов |
| Развёртывание | Docker Compose, Nginx | Запуск клиентского приложения, API, worker и хранилищ |

API валидирует входные данные и вызывает предметные сервисы. Клиентское приложение запрашивает данные через API; состояние сессии и полученные с сервера данные обрабатываются отдельно. Редактируемый дашборд сохраняет расположение виджетов для организации.

## Путь данных

1. Пользователь подключает кабинет WB или Ozon. Ключ сохраняется в зашифрованном виде; в интерфейсе показывается маска.
2. Планировщик или пользователь запускает синхронизацию. API ставит задание в очередь, worker обращается к маркетплейсу и записывает результат в PostgreSQL.
3. После загрузки обновляются затронутые дневные агрегаты; подготовленные представления обеспечивают чтение аналитики и РНП.
4. API отдаёт показатели клиентскому приложению. Статус синхронизации показывает результат загрузки, но сам по себе не подтверждает полноту финансового расчёта.

В реализации присутствуют данные о заказах, продажах, возвратах, финансовых операциях, товарах, рекламе, себестоимости и планах. Для WB и Ozon работают отдельные интеграционные сервисы. [Контракт WB](../data/wb-data-contract.md) подробнее описывает проверки финансового источника; такие же расчётные правила для Ozon в кейсе не определены.

## Доступ и безопасность

Доступ к данным связан с пользователем и организацией. В реализованной основе используются проверка токена, обновление сессии, разграничение доступа к кабинетам, шифрование ключей маркетплейсов, проверка входных данных и журнал событий авторизации. Дополнительные требования к ролям, 2FA, административной публикации правил и аудиту приведены в [SRS](../requirements/srs.md) и [нефункциональных требованиях](../requirements/non-functional-requirements.md).

Подробные границы модулей показаны в [C4](c4-model.md), взаимодействия — в [sequence-диаграммах](sequence-diagrams.md), а интерфейс API — в [OpenAPI](../api/openapi.json).
